## The headline: the Digitone mk1 runs, with its own voices and its own window

The goal was Digitone compatibility with a separate GUI, for
`Digitone_and_Digitone_Keys_OS1.43.syx` (SHA-256 `c5a54cc0…`). All of it is
measured:

- **The app.** `--add` takes 25 s on a fresh home:
  - the cold boot parks at ~130M instructions;
  - the UI is live at ~80M into the intro;
  - the firmware's own first boot settles at ~1300M;
  - the acceptance check passes on the card layout and on the DSP running.

  **Play** opens the Digitone window (`emu/dnpanel.py`), and closing it
  saves `resume.snap`. The same holds for a frozen local build
  (`build-out-dn\digiemu-win64-0.2.0.zip`, self-test ok; this is not a
  release).
- **Sound.** The Digitone's second ColdFire, the "DSP", runs its own code
  (section 7) on a second Unicorn engine (`emu/dsplink.py`), sharing the
  128 KB dual-port RAM with the main CPU. PLAY on the factory pattern:
  - 100% of real time, 0 dropouts, 60–70 ms buffered;
  - one render per audio block (11480 of 11480);
  - RMS ~1.8k, peak ~6.7k;
  - silent at idle.

  The renders run on a thread of their own, using ~80% of a second core.
- **The panel.** All 54 codes were measured by pressing each one. The window
  shows 72 LEDs in 18 groups, and the knobs respond (see encoders below).

[DIGITONE-MK1.md](../../DIGITONE-MK1.md) is the reference write-up. This
page is the story.

## How it went

1. **Porting the Digitakt's symbol rules.** The main OS is a close relative
   of the Digitakt mk1's; the RTOS sits +0x160. Six rules needed a Digitone
   signature: `pend_b`, `intro_done`, `intro_pit3_isr`, `intro_park`,
   `sd_bringup` and `view_activate`. The SSI force tail needed a variant.
   With those, the cold boot, intro and settle ran unchanged.
2. **The settle stuck on "INITIALIZING +DRIVE".** The emulator's unblock
   pass faked the DSP request semaphore (0x4137b70c). Its poster,
   0x400019a0, is a post routine the semaphore scan does not know, so the
   boot task re-uploaded the DSP thousands of times a second. It is now
   never faked. A handshake stand-in (`DspLink`) got the main OS past
   "DSP BOOT FAILURE".
3. **A host crash in the eSDHC model.** The Digitone's first EXT_CSD read
   targets a page nothing had touched. Mapping it inside the memory hook
   resized Unicorn's TLB under the running access. `Machine.poke/peek`
   (`emu/harness.py`) now queue writes to unmapped pages until the page is
   mapped.
4. **The card.** The Digitone has no sample engine, so it has no ekFS.
   `[card] ekfs = false`: the app lays down a blank card, and the
   firmware's first boot initialises it.
5. **The DSP, for real.**
   - Section 7 needs three answers to get through its bring-up: PIT1's
     flag, and the FPGA's INIT_B and DONE pins. Each one was removed in
     turn to confirm it is needed.
   - Its render ISR (vector 96) fires on each PA4 edge the main CPU makes
     per block.
   - The main CPU's render fetches the voices with eDMA channel 47, started
     through SSRT. `emu/edma_sw.py` did not model SSRT until now.
   - The engine needs scoped ISA patches and exception delivery. The
     unscoped patches made a render 123 ms; scoped, it takes 0.22 ms.
6. **Real time.** Rendering inline held the live window at 83–95%. On a
   thread of its own (ctypes releases the GIL inside Unicorn) it runs at
   100%.
7. **The encoders felt dead, on both products.** At one count per wheel
   notch a knob needed ~16 notches before anything moved. The mk1 encoder
   driver has a dead zone: an idle knob's state rests at 48, each count takes
   3, and nothing steps until it is at or below 24. For some parameters,
   every step adds 48 back. `[panel] encoder_counts = 4` sends each notch
   as four counts, and the Digitakt's device file has it too.
8. **A thread race, found by the Linux test run.** The render thread took
   the PA4 latch when it woke, not when the job was handed over. So an edge
   made before the worker woke merged into the previous render: 8485
   renders for 11480 blocks in the first live measurement, about a quarter
   of blocks with stale voices. The main thread now takes the edge. Proof:
   the new test fails on the old code (2 of 4) and passes on the new;
   0 failures in 25 runs on each OS.

## The Digitakt after all of this

- A fresh `--add` takes 23 s, parks at 160M with 10 tasks, settles at 750M
  and is accepted.
- Live at 100% and 0 dropouts. The Digitakt never writes SSRT (0 starts),
  so the SSRT hook cannot touch it.
- The window is unchanged, LOAD SAMPLES included.
- Its factory pattern records silent, but so does the pre-Digitone code
  from the WSL tree, with identical counters (PIT0/2/3 8477/10173/1144 at
  256M). The factory samples are missing; this is not a regression.

## Corrections to earlier write-ups

- STATUS.md listed "Digitone mk1 is recognised but not supported". It now
  runs.
- The first draft of this page's measurements (8485 renders, ~65% of a
  core) was taken before the race fix. The corrected figures are one
  render per block and ~80% of a core.
- `devices/digitone.toml` said `dsplink.py` "stands in" for the DSP. That
  is now the fallback only, used when section 7 is missing.
- A second agent checked the DSP claims against the image bytes
  (docs/FINDINGS.md, "Digitone (mk1) 1.43"). It corrected three of this
  session's own descriptions:
  - Vector 96 is not the render itself. It holds a handshake-phase handler
    first, then a stack trampoline to 0x400008fa.
  - Status 0 means "boot in progress", not "booted".
  - "A 16-count dead zone" was a reading of the measurement, not of the
    code (item 7 above now gives the code's own rule).
